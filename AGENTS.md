# Agent Instructions

## GitHub release notes

When you create or update a GitHub release, describe the version's changes **in the release body itself** — do not point to `WhatsNew.md` with a link only.

- Extract the `# FindRomCover <version> — What's New` section from the repository's `WhatsNew.md` (everything up to the next `# FindRomCover` heading, dropping the trailing `---`) and use it as the release body.
- The extracted section already contains the download list; keep it in the body.
- Only fall back to a changelog link when the section for the tagged version cannot be found (for example when the tag predates the changelog).
- `.github/workflows/release.yml` implements this rule automatically when a `release_*` tag is pushed. Manual releases (`gh release create` / `gh release edit`) must follow the same rule.

## Documentation

- `docs/` feeds both the GitHub Pages site (MkDocs Material, navigation in `mkdocs.yml`) and the GitHub wiki (generated by `scripts/Sync-Wiki.ps1`, sidebar from the same script). Keep both side menus in sync when adding or renaming pages.
- Release documentation lives in `WhatsNew.md`, `docs/release-notes.md`, and `README.md`; update all three for every release.

## Release and deployment routine

Follow this routine when preparing a version release. The release is not complete until CI, Pages, the wiki, and the GitHub release are all verified.

### 1. Review and prepare

1. Review every commit since the previous `release_*` tag (`git log --oneline <previous>..HEAD`) for regressions, especially changes to image conversion, WebView handling, AI requests, release scripts, and CI. Fix any bug found before releasing.
2. Bump the version in both project files:
   - `FindRomCover/FindRomCover.csproj`: `Version`, `AssemblyVersion`, `FileVersion`.
   - `FindRomCover.Tests/FindRomCover.Tests.csproj`: `AssemblyVersion`, `FileVersion`.
3. Add a new top section to `WhatsNew.md`:
   - Heading: `# FindRomCover <version> - What's New`
   - Include what changed, the download list, and the runtime note.
   - Keep the previous version section below it.
4. Add the same release notes (adapted for the documentation site) to the top of `docs/release-notes.md`.
5. Update `README.md`: the What's New link, a short "What's New in <minor>" section, and any current-version references. Badges must remain at the top of the file.
6. Update current-version references in `docs/` (for example `docs/faq.md`, `docs/development/building.md`, `docs/development/ci-cd.md`, `docs/configuration/bug-reports.md`). Do not rewrite historical release notes.
7. Verify both documentation side menus:
   - `mkdocs.yml` `nav` contains every page under `docs/`.
   - `scripts/Sync-Wiki.ps1` `$sidebarSections` contains every page and no missing paths.
   The wiki and the Pages site must share the same section structure.

### 2. Validate

```powershell
dotnet restore CSharp_FindRomCover.sln
dotnet build CSharp_FindRomCover.sln -c Release -warnaserror
dotnet test CSharp_FindRomCover.sln -c Release --no-build
dotnet format CSharp_FindRomCover.sln --verify-no-changes
mkdocs build --strict
pwsh ./scripts/Sync-Wiki.ps1 -OutputPath wiki-out
actionlint .github/workflows/*.yml   # when actionlint is available
```

All tests must pass and the build must be warning-free.

### 3. Build local release bundles

Build the same five framework-dependent single-file archives that `release.yml` publishes:

`win-x64`, `win-arm64`, `linux-x64`, `linux-arm64`, `osx-arm64`.

For each RID:

```powershell
dotnet publish FindRomCover/FindRomCover.csproj -c Release -r <rid> `
  --self-contained false `
  -p:PublishSingleFile=true `
  -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:Version=<version> -p:AssemblyVersion=<version> -p:FileVersion=<version> `
  -p:DebugType=None -p:DebugSymbols=false `
  -o "bundle-stage/<version>/<rid>/publish"
```

Then stage and archive:

1. Copy the publish output into `bundle-stage/<version>/<rid>/bundle`.
2. Copy `LICENSE.txt`, `README.md`, and `WhatsNew.md` into that staging folder.
3. Remove any `*.pdb` files.
4. Create `FindRomCover/bin/Release/release_<version>_<rid>.zip` from the staged contents.
5. **Do not delete existing files in `FindRomCover/bin/Release`.** Historical bundles are kept there; only create or refresh the current version's archives.
6. Do not embed the .NET runtime; the bundles stay framework-dependent. Keep the `release_<version>_<rid>.zip` naming because the release page and update flow depend on the tag/asset convention.

### 4. Push and verify the branch

1. Commit the release changes and push `master`.
2. Wait for the `CI`, `CodeQL`, and `Docs` workflows to pass.
3. Confirm the Pages site returns HTTP 200 and the wiki repository received the sync commit.
4. The `master safety` ruleset blocks force pushes/deletion. The `master status checks` ruleset has an administrator bypass for direct pushes; do not force-push or delete `master`.

### 5. Tag and publish

```powershell
git tag release_<version>
git push origin release_<version>
```

The `release.yml` workflow:

1. validates the tag against `Version`, `AssemblyVersion`, and `FileVersion` in both project files;
2. builds and tests the tagged commit with warnings as errors;
3. builds the five native-runner bundles;
4. creates the GitHub release with the tag's `WhatsNew.md` section as the body and the archives attached.

Wait for the workflow to pass, then verify:

- the release exists, is published, and has all five assets;
- the release body is the `# FindRomCover <version> - What's New` section, including the download list;
- the Pages site and wiki still resolve after the release.

The in-app update checker reads the latest release's `tag_name`; keep the `release_<major>.<minor>.<patch>` format.
